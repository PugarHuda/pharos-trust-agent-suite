# Aligning a2a-mesh with ERC-8004 (Trustless Agents)

ERC-8004 ("Trustless Agents") went live on Ethereum mainnet on **2026-01-29**. It standardizes
**identity + reputation + validation** for AI agents as a trustless extension of Google's A2A protocol,
and — crucially — **defers payments to x402**. That is almost exactly this suite's architecture, so
adopting ERC-8004 is a high-leverage, low-effort move: we already implement the hard part.

Refs: [EIP-8004](https://eips.ethereum.org/EIPS/eip-8004) ·
[Quicknode guide](https://blog.quicknode.com/erc-8004-a-developers-guide-to-trustless-ai-agent-identity/)

## The three registries → our suite

| ERC-8004 registry | What it standardizes | Our equivalent |
|-------------------|----------------------|----------------|
| **Identity** (ERC-721 `agentId`, `agentURI` → agent card with endpoints + `agentWallet`) | discoverable agent identity | `ServiceRegistry` (owner + tag + endpoint + price). The service owner is the agent; the endpoint is its A2A/MCP card entry. |
| **Reputation** (`giveFeedback(agentId, value, valueDecimals, tag1, tag2, …)`, **submitter ≠ agent owner**) | client feedback signals | `Reputation` — **payment-gated** `rate(ref, score)` where only the **paying** counterparty (payer ≠ provider) can rate, keyed by (payer, ref). |
| **Validation** (`validationRequest`/`validationResponse`, response 0–100) | independent verification of agent work | `stylus-compute` — verifiable on-chain compute (a risk/quality score) is a natural ERC-8004 **validator**. |
| **Payments** (explicitly **out of scope**, deferred to x402) | — | `x402-facilitator` (gasless EIP-3009 settle). |

## Why our reputation is a *stronger* ERC-8004 Reputation Registry

ERC-8004's only anti-gaming rule is "the submitter cannot be the agent owner/operator." We enforce that
**and more**: a rating is accepted only from the address that **actually paid** for the interaction
(EIP-712 payer signature, recorded against a settlement `ref`, keyed by `(payer, ref)` so a `ref` can't
be griefed). So migrating to ERC-8004's interface keeps all our guarantees and adds standard interop.

## Field mapping (rate → giveFeedback)

| ERC-8004 `giveFeedback` arg | Our value |
|------------------------------|-----------|
| `agentId` | the provider (agent) — as an ERC-721 id once Identity is adopted, or the provider address in the adapter |
| `value` / `valueDecimals` | `score` mapped to the "starred" 0–100 metric: `value = score * 20`, `valueDecimals = 0` |
| `tag1` / `tag2` | `"x402"` / the service tag (e.g. `price-feed`) |
| `endpoint` | the service endpoint from `ServiceRegistry` |
| `feedbackURI` / `feedbackHash` | optional off-chain review JSON + its keccak hash (future) |
| submitter ≠ owner rule | enforced *and strengthened* to payer-gated |

`getSummary(agentId, clients, tag1, tag2) → (count, summaryValue, summaryValueDecimals)` maps to our
`scoreOf(provider)` / `ratingCount(provider)`.

## Adoption path (cheap → high interop)

1. **Interface adapter (this PR):** ship `IReputationRegistry8004.sol` (the standard interface) and a
   read adapter that exposes `getSummary`/`readFeedback` over our `Reputation` so ERC-8004 consumers can
   already read our scores. *No redeploy of the core needed.*
2. **Identity (next):** mint an ERC-721 `agentId` per provider whose `agentURI` is an agent card
   embedding the `ServiceRegistry` endpoint + `agentWallet` (the payment address x402 settles to).
3. **Validation (next):** register `stylus-compute` as an ERC-8004 validator so a risk/quality score is
   posted via `validationResponse`.

This positions the suite as a **Pharos-native ERC-8004 + x402 implementation** — the exact trust stack
the broader agent economy is standardizing on.
